# WordClash 项目优化建议

扫描时间：2026-08-27

说明：本次结论基于静态代码扫描得出，未启动项目、未运行脚本、未做运行时验证。

## 一、建议优先处理

### 1. 对对碰加权抽样存在概率偏移

- **位置：** `src/stores/game.js:74-90`
- **现象：** `selectWeighted()` 只在进入循环前计算了一次 `totalScore`，但每次抽中后都会从 `remaining` 中移除元素，后续轮次没有同步重算总权重。
- **影响：** 抽样分布会失真，剩余元素越少偏差越明显，末尾元素可能被异常偏向，导致「新词 / 错词优先」策略不稳定。
- **建议：** 每轮重新计算当前剩余池的总权重，或者改成更直接的「累积权重 + 逐轮重建」写法，保证抽样与评分模型一致。

### 2. 文章解析过程中存在高频持久化写入

- **位置：** `src/views/ArticleReader.vue:187-195`、`src/views/ArticleReader.vue:211-219`
- **现象：** 每完成一段翻译、每完成一句拆解，都会调用一次 `articlesStore.updateArticle()`，而该方法内部会立刻 `persist()` 到 `localStorage`。
- **影响：**
  - 长文场景下会产生大量同步 `localStorage` 写入；
  - 主线程更容易卡顿；
  - 更容易触发配额上限；
  - 解析时间越长，写放大越明显。
- **建议：**
  - 将渐进式 UI 更新和持久化拆开；
  - UI 层允许先更新内存状态；
  - 按批次、节流或阶段完成后再落盘；
  - 可考虑只在概要完成、段落翻译完成、逐句拆解完成这 3 个阶段持久化。

### 3. 文章模块重复调用 `parseWord()`，浪费配额和等待时间

- **位置：** `src/views/ArticleReader.vue:164-172`、`src/views/ArticleReader.vue:319-341`
- **现象：** 文章导入后已经对生词做过一次预解析并缓存到 `wordDetails`，但「入库选中单词」时又重新逐个调用 `parseWord()`。
- **影响：**
  - 同一单词重复请求 AI；
  - 增加 API 成本与限流概率；
  - 用户等待时间变长。
- **建议：** 入库时优先复用 `current.wordDetails`、本地词库和组件缓存；仅对确实缺失的数据补调 API。

## 二、建议尽快优化

### 4. Store 初始化分散在多个页面，入口不统一

- **位置：** `src/views/WordInput.vue:47`、`src/views/WordBank.vue:47`、`src/views/MatchingGame.vue:106`、`src/views/Analysis.vue:56`、`src/views/ArticleReader.vue:16-17`
- **现象：** `wordsStore.init()` / `articlesStore.init()` 被多个页面重复调用。
- **影响：**
  - 初始化职责分散；
  - 后续一旦加入异步初始化、数据迁移、版本升级逻辑，维护成本会明显增加；
  - 页面首次进入和路由切换时更难追踪状态来源。
- **建议：** 把初始化前移到应用入口或单独的 bootstrap 层，只做一次；页面只消费状态，不负责装载数据。

### 5. 文章解析并发数与项目文档约定不一致

- **位置：** `src/views/ArticleReader.vue:66`、`src/views/ArticleReader.vue:182`、`src/views/ArticleReader.vue:200`
- **现象：** 当前代码并发数是 `6`，但项目文档中写的是「并发 3、逐段渐进更新」。
- **影响：**
  - 文档和实现不一致；
  - 限流、超时、配额消耗更难预估；
  - 后续排查线上问题时容易误判。
- **建议：** 统一文档与实现。如果以稳定性优先，建议回到 `3`；如果确认 `6` 是新的策略，记得同步更新项目文档。

### 6. 句子切分策略过于粗糙

- **位置：** `src/views/ArticleReader.vue:204`
- **现象：** 逐句拆解直接使用 `/[.!?]+/` 分割。
- **影响：**
  - 缩写、数字、小数、引号、复杂标点场景容易误切；
  - 影响逐句拆解质量与后续缓存命中；
  - AI 上下文被错误切断后，结果稳定性会下降。
- **建议：** 抽出独立的英文句子切分工具函数，至少补齐缩写和常见标点的保护逻辑；后续也便于单独维护。

### 7. `storage.js` 存在未完成/未使用的旧抽象

- **位置：** `src/services/storage.js:3-18`
- **现象：**
  - `db` 未使用；
  - `ensureDir()` 是空函数；
  - `loadWords()` 读取 `data/words.json`，但当前 store 实际走的是 `localStorage`；
  - 单词存储 key 仍叫 `wordmatch-words`，与项目名 `WordClash` 不一致。
- **影响：**
  - 读代码时容易误判真实数据流；
  - 后续做数据迁移或备份恢复时容易踩坑；
  - 命名不一致不利于长期维护。
- **建议：**
  - 清理死代码和过时注释；
  - 明确单词数据的唯一事实来源；
  - 将存储 key 统一为 `wordclash-*` 风格，并考虑加版本号。

## 三、体验和可维护性优化

### 8. 页面层直接修改 store 状态，建议收口为 action

- **位置：** `src/views/MatchingGame.vue:35-38`
- **现象：** 页面中直接写 `gameStore.selectedLeft = null`、`gameStore.selectedRight = null`、`gameStore.matchResult = null`。
- **影响：**
  - 状态变更入口不统一；
  - 以后加动画、埋点、日志、撤销逻辑时不方便；
  - 容易让页面承担过多业务状态职责。
- **建议：** 在 `game store` 中新增 `resetSelection()` / `resolveWrongMatch()` 一类 action，把状态收口到 store 内部。

### 9. 当前交互仍依赖原生 `alert` / `confirm`

- **位置：** `src/views/MatchingGame.vue:17`、`src/views/WordBank.vue:41`、`src/views/ArticleReader.vue:248`
- **现象：** 游戏提示和删除确认仍然使用浏览器原生弹窗。
- **影响：**
  - 体验割裂；
  - 样式不可控；
  - 后续如果加移动端适配或无障碍支持会比较被动。
- **建议：** 抽一个轻量的全局提示/确认组件，统一用于错误提示、删除确认、成功反馈。

### 10. 文章与单词模块都缺少统一的数据版本迁移机制

- **位置：** `src/stores/words.js`、`src/stores/articles.js`、`src/services/storage.js`
- **现象：** 当前本地持久化直接读写 JSON，没有 schema version 或 migration 流程。
- **影响：**
  - 后续新增字段（如默写记录、文章学习状态）时，旧数据兼容会越来越脆；
  - 线上老用户本地缓存可能出现字段缺失。
- **建议：** 为本地存储增加 `version` 字段和迁移函数，在 `init()` 时统一修复旧数据结构。
- **当前决策记录：**
  - 该项暂不按“兼容迁移”方向实施；
  - 后续将改为“仅保留当前正式数据结构，不兼容旧数据”；
  - 如旧本地数据触发异常，由使用者手动清理本地存储或重新导入数据文件。

### 11. 全局样式变量已初步成型，但还没有形成真正的设计令牌体系

- **位置：** `src/App.vue`
- **现象：** 颜色、圆角、阴影有统一变量，但页面内部仍有不少直接写死的颜色值，如浅黄、浅蓝、浅红、浅绿等。
- **影响：**
  - 主题切换、视觉统一、批量调整成本偏高；
  - 后续增加暗色模式或品牌色方案时会比较碎。
- **建议：** 把状态色、提示色、标签色、面板色也继续抽成 CSS 变量，避免页面内散落硬编码。

## 四、可清理项

### 12. 仓库中存在疑似无引用文件

- **位置：** `test.js`、`WordClash.txt`
- **现象：** 当前代码检索中没有看到它们被项目入口引用。
- **影响：**
  - 容易让人误以为还有隐藏流程；
  - 增加仓库噪音。
- **建议：** 确认用途后决定保留、迁移到 `docs/`，或直接清理。

## 五、建议的处理顺序

1. 先修 `game.js` 的加权抽样问题。
2. 再优化 `ArticleReader.vue` 的持久化频率和重复 `parseWord()` 调用。
3. 然后统一 store 初始化入口和本地存储结构。
4. 最后处理弹窗体验、样式变量和仓库清理项。

## 六、补充说明

- 当前项目整体结构已经有比较清晰的页面、store、服务层分层，适合继续往「轻量但可持续迭代」的方向收敛。
- 下一阶段如果要接入「默写游戏」，建议优先补上：
  - 本地数据版本迁移；
  - 通用提示/确认组件；
  - 更稳定的 store 初始化与持久化策略。
