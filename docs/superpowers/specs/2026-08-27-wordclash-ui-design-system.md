# WordClash 界面设计规范

更新时间：2026-08-27

说明：本规范用于统一 WordClash 后续所有页面与组件的设计语言，作为界面重构、样式抽象、交互收口和组件新增时的唯一视觉基线。

## 1. 设计目标

WordClash 不是内容社区，也不是娱乐化游戏产品。它的产品定位应当是：

- **个人英语学习工作台**
- **高可读、低噪音、轻专业**
- **优先服务学习效率，而不是装饰性视觉**

本项目的界面目标不是“看起来炫”，而是做到下面 4 件事：

1. 用户进入页面后，能在 3 秒内理解当前页的主要任务。
2. 主要操作必须稳定突出，次要信息不能抢视觉。
3. 同类组件在不同页面里保持一致，不允许同义不同形。
4. 界面要支持长期迭代，后续新增默写页时无需重新发明一套样式。

## 2. 当前问题总结

基于当前项目状态，界面层面存在以下核心问题：

- 已经有一批基础变量，但还没有形成完整设计令牌体系。
- 页面风格开始统一，但仍偏“经验型 UI”，不是“规范驱动 UI”。
- 反馈方式仍混有原生 `alert / confirm`，体验割裂。
- 某些视觉决策只停留在单页面层面，缺少全站规则。
- 状态色、说明块、交互层、弹层、空状态尚未被系统化定义。

后续所有 UI 改动都应优先解决“无规范导致页面漂移”的问题，而不是继续零散修样式。

## 3. 品牌气质

### 3.1 气质关键词

- 稳定
- 清晰
- 专注
- 轻专业
- 可信赖

### 3.2 禁止方向

- 过强游戏化
- 过重插画化
- 过亮高饱和
- 过密信息堆叠
- 为了“设计感”牺牲阅读效率

### 3.3 推荐视觉印象

- 主体为浅色工作台
- 导航区允许更深色，以建立结构层次
- 内容区优先使用大留白、清晰模块和稳定边界
- 强调“阅读”和“学习管理”，不是“营销落地页”

## 4. 视觉体系

## 4.1 色彩角色

颜色不按“好看”命名，只按职责命名。后续实现时必须以语义变量使用。

- **Canvas / 背景层**
  - `--color-bg`
  - `--color-bg-soft`
- **Surface / 面板层**
  - `--color-surface`
  - `--color-surface-alt`
- **Text / 文本层**
  - `--color-text`
  - `--color-text-secondary`
  - `--color-text-muted`
- **Brand / 品牌主色**
  - `--color-primary`
  - `--color-primary-dark`
  - `--color-primary-light`
  - `--color-accent`
- **Feedback / 状态色**
  - `--color-success`
  - `--color-success-light`
  - `--color-warning`
  - `--color-warning-light`
  - `--color-danger`
  - `--color-danger-light`
- **Stroke / 边界层**
  - `--color-border`
  - `--color-border-strong`

### 4.2 用色原则

1. **主色只服务关键动作与关键识别**  
   例如：主按钮、激活导航、聚焦态、页眉 eyebrow、重要标签。

2. **状态色只表达状态，不承担装饰任务**  
   成功色只用于成功提示、已完成、正确反馈；不能拿来做普通卡片背景。

3. **正文阅读区域避免强色块**  
   文章页正文区要保证长时间阅读舒适，不能出现大面积高饱和背景。

4. **同一页面最多 1 个主视觉焦点 + 1 个辅助强调色**  
   不能一个页面同时让蓝、黄、绿、红都在抢注意力。

### 4.3 状态层规范

- 成功：用于“已完成、已入库、回答正确”
- 警告：用于“待注意、重点词、轻提醒”
- 危险：用于“删除、失败、错误、不可逆操作”
- 信息：用于“处理中、阶段状态、进度提示”

状态块、标签、提示条、弹窗按钮必须保持统一颜色语义。

## 5. 字体与排版

## 5.1 字体层级

- `Page Title`：32-36px，700
- `Section Title`：18-22px，700
- `Card Title`：16-18px，600/700
- `Body`：14-16px，400/500
- `Meta`：12-13px，400/500
- `Eyebrow`：11-12px，700，全大写或小型英文标签

## 5.2 排版原则

1. 页面标题必须明确表达“当前页要做什么”。
2. 描述文案用于降低理解成本，不用于堆概念。
3. 正文说明尽量控制在 2-3 行内。
4. 长文本优先提升行高，而不是提升字号。
5. 英文单词、音标、标签、统计值要形成明显层次，不可视觉等权。

## 6. 间距、圆角、边框、阴影

## 6.1 间距体系

建议统一为 4 的倍数体系，常用值如下：

- `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48`

优先级建议：

- 组件内部小间距：`8 / 12`
- 卡片内容间距：`16 / 20 / 24`
- 页面模块间距：`24 / 32`
- 页面外边距：`36 / 40 / 48`

## 6.2 圆角体系

- 小组件：`12`
- 普通卡片 / 输入框 / 按钮：`14-18`
- 大面板 / 弹层：`20-24`

原则：同一页面不要混用太多圆角级别，视觉上最多维持 3 档。

## 6.3 边框与阴影

- 默认优先 `浅边框 + 轻阴影`
- 强交互容器可用 `更强边框`
- 阴影只承担层级表达，不做视觉炫技

界面默认应偏“边界稳定”，而不是“漂浮悬空”。

## 7. 页面骨架规范

所有主页面默认采用同一套骨架：

1. `Page Header`
2. `Summary / Stats`
3. `Primary Workspace`
4. `Secondary Supporting Area`
5. `Feedback / Empty / Loading`

### 7.1 页头结构

页头必须包含：

- `eyebrow`
- `page title`
- `page desc`
- 如有必要的 `page actions`

页头职责：

- 说明当前页面目标
- 明确主操作方向
- 不承担复杂业务内容

### 7.2 页面类型模板

WordClash 后续页面只能在以下几类模板中选：

- **工作台页**
  - 适用：文章阅读、单词录入
- **列表管理页**
  - 适用：单词库
- **训练页**
  - 适用：对对碰、默写游戏
- **分析页**
  - 适用：学习分析

不建议每个页面都重新发明布局。

## 8. 核心组件规范

## 8.1 按钮

按钮只保留 4 类：

- `Primary`
- `Secondary`
- `Ghost`
- `Danger`

规则：

- 一个视区里只能有一个真正的主按钮
- 删除操作不能伪装成普通按钮
- 文本按钮只用于弱操作
- 按钮高度、圆角、字重必须统一

## 8.2 表单

输入组件包括：

- 输入框
- 文本域
- 选择器
- 复选框
- 单选框
- 文件触发器

规则：

- 焦点态必须统一
- 错误态、禁用态必须统一
- 输入区和说明文案之间必须保留清晰上下级关系
- 文件导入按钮应视觉上与普通按钮一致，不能像浏览器原生控件

## 8.3 卡片

卡片分 3 类：

- **数据卡**：展示统计值
- **工作卡**：承载操作流程
- **信息卡**：承载解释、提示、细节

规则：

- 卡片内容必须有主次，不允许所有文本同等突出
- 卡片不是“加边框的 div”，必须有明确职责
- 卡片内部信息密度应围绕任务，而不是围绕样式

## 8.4 标签与状态块

标签分两类：

- `chip`：轻量、识别性标签
- `tag`：状态或属性标签

规则：

- 标签只表达一个概念
- 不允许用标签承载整句说明
- 同一行标签数量建议不超过 4 个

## 8.5 空状态

空状态必须包含：

- 一句明确标题
- 一句下一步引导

不要使用“暂无数据”这种无行动价值的空文案。

## 8.6 反馈系统

当前项目后续必须废弃原生 `alert / confirm`，统一为站内反馈系统，至少包含：

- Toast：轻量成功/失败反馈
- Inline Notice：页面内状态提示
- Confirm Dialog：删除、覆盖、不可逆操作确认
- Modal：需要聚焦完成的单次任务

其中：

- 删除文章
- 删除单词
- 重要覆盖操作
- 导入失败

都不应继续使用浏览器原生弹窗。

## 9. 页面级规范

## 9.1 单词录入页

定位：**快速收词工作区**

必须突出：

- 单词录入动作
- 最新录入反馈
- 最近录入列表

不应让统计卡压过主输入区的视觉权重。

## 9.2 单词库页

定位：**词库管理页**

必须突出：

- 搜索与排序
- 列表扫描效率
- 单词详情展开

不应把它做成“杂乱资料堆”，而应像一个高可读的知识列表。

## 9.3 对对碰页

定位：**即时训练页**

必须突出：

- 当前轮次状态
- 正误反馈
- 清晰的卡片点击层级

它可以有轻微游戏感，但主体仍应属于学习产品，而不是休闲游戏。

## 9.4 学习分析页

定位：**复盘页**

必须突出：

- 指标总览
- AI 总结
- 弱项与已掌握项分区

分析页的价值在于“帮助下一步决策”，不是只堆数字。

## 9.5 文章阅读页

定位：**阅读工作台**

推荐固定成 6 区结构：

1. 导入区
2. 历史区
3. 概览区
4. 生词管理区
5. 正文精读区
6. 理解题区

其中正文精读区应永远保持最高阅读优先级，不能被侧边控制区抢走注意力。

## 10. 文案规范

界面文案必须满足：

- 短
- 明确
- 指向动作
- 不装饰性堆砌

### 推荐表达

- `开始精读`
- `加入单词库`
- `生成理解题`
- `已入库 3 个`
- `正在翻译段落 2/6`

### 不推荐表达

- `立即开启专属学习之旅`
- `恭喜你成功完成当前内容处理`
- `让我们一起继续探索吧`

WordClash 的语气应该是可靠、克制、明确，而不是运营化。

## 11. 实现层要求

为了让规范真正落地，后续代码实现应遵守以下规则：

1. 全局样式中的颜色、圆角、阴影必须继续抽成语义令牌。
2. 页面内部禁止继续散落硬编码状态色。
3. 反馈类交互必须抽成统一组件，而不是局部各写一套。
4. 页面新增模块前，先判断它属于现有哪一种页面模板。
5. 后续默写页必须沿用本规范，不允许再起一套新视觉语言。

## 12. 本项目的下一步设计工作

这份规范文档不是最终稿，而是第一版可执行基线。建议后续按这个顺序推进：

1. 先抽离真正的设计令牌体系
2. 再补统一的反馈系统（toast / confirm / modal）
3. 然后统一页面模板
4. 最后再逐页细化视觉精度

## 13. 关于数据兼容的已确认决策

此条不是视觉规范本身，但与后续实现边界有关，故在此记录：

- **已确认：后续处理数据结构时，不对旧本地数据做兼容迁移。**
- **策略：只保留当前正式数据结构，删除 legacy 兼容逻辑。**
- **出现旧数据异常时，由使用者手动清理本地存储或重新导入数据文件。**

这个决策的目标是保证存储层代码始终简洁、直接、无冗余。
